## Context

Forge publishes `pipeline.stage-complete.{feature_id}` to the `PIPELINE` JetStream stream (7-day retention per ADR-SP-017). Jarvis subscribes so it can surface progress back to Rich. The JetStream consumer-shape question splits along three axes:

1. **Durable vs ephemeral** — does the consumer survive Jarvis restart with a stable name + state?
2. **Push vs pull** — does NATS dispatch messages to a callback (push), or does Jarvis explicitly fetch (pull)?
3. **Deliver policy** — does the consumer replay history (`ALL`), start at the next published message (`NEW`), or pick up by sequence / start-time?

Forge's own consumer for `pipeline.build-queued.>` is **durable, pull, `DeliverPolicy.ALL`** (per Forge's API-nats-pipeline-events.md §2.2) — that's the right choice for Forge because Forge owns build state and must not lose a build trigger across restart. Jarvis's situation is different:

- Jarvis is the *progress-display* side, not the state-owning side.
- The notifications surface to a CLI between prompts; if Jarvis was down when a stage event fired, replaying it post-restart isn't useful — the operator has moved on (or restarted *because* of the same Forge problem).
- The originating session may not even exist after a restart (sessions are ephemeral per ADR-ARCH-009).

ADR-ARCH-026 says single instance per user — there's no concurrent-Jarvis case to worry about; one ephemeral consumer per Jarvis process is the entire footprint.

## Decision

The `pipeline.stage-complete.>` JetStream consumer is:

1. **Ephemeral** — no `durable=` argument. The consumer name is auto-generated by `nats-py`; it's cleaned up automatically when the subscription drains. No across-restart state.
2. **Push** — uses `js.subscribe(subject, cb=self._on_message)` (push semantics). Async callback dispatch keeps the in-flight notification path simple; the alternative (pull-fetch loop) adds machinery for a single-instance, low-volume signal.
3. **`DeliverPolicy.ALL`** *(revised 2026-05-01)* — workqueue retention on the canonical PIPELINE stream rejects any other delivery policy with `code=10101`. The consumer drains its filter slice (`pipeline.stage-complete.>`) on every delivery; the no-replay-on-restart UX is preserved structurally rather than via the policy enum (see [Workqueue interaction](#workqueue-interaction-2026-05-01-revision)).
4. **Auto-ack** — no `manual_ack=True`. The bridge to the CLI is in-process, not durable; redelivery cannot improve the outcome. Failures upstream of the correlation lookup drop silently; failures downstream are caught by `RoutingHistoryWriter`'s WARN-only path. Auto-ack also drives workqueue's retention behaviour: each delivered message is removed from the stream as soon as the callback returns, so Jarvis's slice of the stream is empty in steady state.

## Rationale

- **Ephemeral matches Jarvis's session-ephemeral posture.** ADR-ARCH-009 already pins thread-per-session ephemeral state. Durable consumers would imply a cross-restart UX that Jarvis doesn't otherwise offer.
- **`DeliverPolicy.ALL` is the only valid policy on the canonical workqueue.** `nats-infrastructure/streams/stream-definitions.json` provisions `PIPELINE` with `retention=workqueue`; nats-py rejects any non-`ALL` consumer policy with `code=10101 consumer must be deliver all on workqueue stream`. The original v1 of this DDR chose `DeliverPolicy.NEW` on the assumption that `PIPELINE` was a `LimitsPolicy` stream — that assumption was incorrect from the moment `nats-infrastructure` standardised on workqueue retention for the dev pipeline (see canonical config below).
- **Workqueue + auto-ack + DDR-028 in-memory correlation map together preserve the original "no replay UX surprise" property** — see [Workqueue interaction](#workqueue-interaction-2026-05-01-revision) below.
- **Push is the simpler shape for callback-driven processing.** Pull-fetch would require an explicit asyncio loop (start, fetch, dispatch, repeat) and a graceful-shutdown signal; push hands the dispatch problem to nats-py.
- **Auto-ack because redelivery has no upside.** The notification queue is in-memory (DDR-028) and not durable across restart. A redelivered event would arrive after the subscriber's restart-fresh state with no correlation entry — and would drop silently anyway. No lost durability; less ack machinery. On a workqueue stream auto-ack also drains the message immediately so the stream's `state.messages` for this consumer's slice stays at zero in steady state.
- **Forge's crash-recovery is independent.** Forge owns its own build-state machine and its own consumer (`forge-prod` durable on `pipeline.dispatch.*`, verified `delivered=1, acked=1, num_pending=0` on the GB10 2026-05-01 run — workqueue retention is what removes the message after Forge acks so `state.messages=0`). A Jarvis restart loses Jarvis's view of in-flight notifications but doesn't affect the build itself.

## Workqueue interaction (2026-05-01 revision)

The canonical PIPELINE stream:

```json
{
  "name": "PIPELINE",
  "subjects": ["pipeline.>"],
  "retention": "work",
  "max_age": "7d",
  "max_msgs": 10000,
  "storage": "file",
  "replicas": 1
}
```

(verbatim from `nats-infrastructure/streams/stream-definitions.json`.)

**Why workqueue is the right shape for `PIPELINE`.** Forge's `forge-prod` durable consumes `pipeline.dispatch.*` and depends on workqueue's "ack-deletes" semantics for build-trigger draining (each dispatch is processed exactly once, then removed from the stream). Switching `PIPELINE` to `LimitsPolicy` is therefore non-trivial — it would change Forge's correctness model, not just Jarvis's UX — and is out of scope for this DDR.

**How "no replay UX surprise" is preserved with `deliver_policy=ALL`.**

The original `deliver_policy=NEW` rationale was: prevent a torrent of replayed `stage X completed` lines on every Jarvis restart because the 7-day `LimitsPolicy` retention would otherwise hand Jarvis the entire backlog. With workqueue retention, that torrent never materialises — and even if it did, the in-memory correlation map prevents UI surfacing:

1. **Auto-ack drains the stream slice.** Workqueue retention deletes a message once any consumer acks it. Jarvis's filter is `pipeline.stage-complete.>` (no overlap with Forge's `pipeline.dispatch.*` filter, so workqueue's "one consumer per matching subject" rule is satisfied). Auto-ack means each delivery is removed from the stream the moment `_on_message` returns, so in steady-state Jarvis's slice is empty.
2. **Restart-replay is bounded by what was unacked.** If Jarvis is down while Forge publishes stage-complete events, the messages accumulate (workqueue keeps them until any consumer acks them). On Jarvis restart with `deliver_policy=ALL`, those backlogged messages are delivered and immediately drained.
3. **DDR-028 correlation map is in-memory.** Every backlogged message hits the `correlation_id not found` silent-drop branch in `_handle_message` (the in-memory map was lost on restart per DDR-028). The operator sees no UI lines for stage events on builds they triggered before the restart — same observable behaviour as `deliver_policy=NEW` would have produced if it were a valid choice.
4. **Auto-ack still drains the message.** The silent-drop branch returns from the callback normally, the message is acked, and workqueue removes it. Net effect: silent drain on restart, no UX disruption, clean stream.

Result: the operator's mental model ("show me what happens *from now*") is preserved. The mechanism shifted from delivery-policy-driven to retention+correlation-map-driven, but the UX invariant is unchanged.

## Alternatives considered

| Option | Why not |
|---|---|
| `DeliverPolicy.NEW` *(original v1 choice)* | Rejected by nats-py with `code=10101` against the canonical workqueue stream — invalid against current `nats-infrastructure` provisioning. The 2026-05-01 GB10 run captured this as `jarvis_forge_subscriber_start_failed`. |
| Switch `PIPELINE` to `LimitsPolicy` | Out of scope: Forge's `forge-prod` durable depends on workqueue ack-deletes semantics for build-trigger draining (verified `delivered=1, acked=1, num_pending=0` on GB10). Changing retention would change Forge's correctness model, not just Jarvis's UX. |
| Durable pull consumer (mirror Forge's pattern) | Adds across-restart state Jarvis doesn't otherwise carry; doesn't improve the bridge UX (in-memory bridge doesn't persist anyway); workqueue still requires `deliver_policy=ALL` regardless. |
| Durable push consumer with `DeliverPolicy.ALL` | Solves an across-restart consumer-name-stability problem Jarvis doesn't have (single instance per ADR-ARCH-026); also adds a JetStream KV state we'd need to garbage-collect on uninstall. |
| Ephemeral pull with manual fetch loop | More machinery for a low-volume signal; the loop's shutdown logic interacts with `lifecycle.shutdown`'s 5s drain budget; push handles this cleanly. |
| Ephemeral push + manual ack (drop-on-failure) | Manual-ack adds redelivery semantics without the durability backing them; auto-ack is the simpler, less-surprising default and is what drives workqueue's stream-cleanup behaviour. |
| Subscribe to `pipeline.>` (everything) | Surfaces 8 subject families when v1 only renders `stage-complete`; also breaks workqueue's "one consumer per matching subject" rule (Forge already consumes `pipeline.dispatch.*`). |

## Consequences

- `ForgeNotificationsSubscriber.start()` calls `js.subscribe("pipeline.stage-complete.>", deliver_policy=DeliverPolicy.ALL, cb=self._on_message)` — the subject + policy are the entire transport contract. The helper that lazy-loads the enum is named `_get_deliver_policy_all` (renamed 2026-05-01 from `_get_deliver_policy_new` per TASK-FRR-001).
- `tests/test_lifecycle_nats_subscriptions.py` (TASK-FRR-001 RED→GREEN) asserts the consumer attaches cleanly against the canonical workqueue stream (no `code=10101`) and that `capabilities_mode == "live"` (not the DDR-021 stub fallback) once the canonical KV bind succeeds.
- `tests/test_forge_notifications_integration.py` asserts: stage events emitted *before* subscription do not surface (workqueue + ephemeral consumer + `DeliverPolicy.ALL` only sees what's still in the stream when it attaches; under steady-state operation the stream is empty for this filter); events emitted *after* subscription do surface; the consumer is gone after `stop()`.
- Operator restart UX: stage events fired during the outage replay through the consumer on restart but hit the DDR-028 in-memory correlation map's silent-drop branch, then drain via auto-ack. Net observable: same as `deliver_policy=NEW` would have produced if it were a valid choice on a workqueue stream — no surprise lines, just clean drainage.
- Forge's terminal `pipeline.build-complete.{feature_id}` event still lands on PIPELINE — Jarvis doesn't subscribe in v1 (filter is `pipeline.stage-complete.>`) so doesn't see it.
- v1.5 candidate: durable `notifications.cli` consumer if cross-session continuity becomes a real operational need (FEAT-J006 / FEAT-J009 territory). Append-only DDR.
- The PIPELINE workqueue retention is unaffected by this consumer — ephemeral consumers don't pin retention; auto-ack drains messages on this consumer's slice; Forge's own consumer drains its own slice. Steady-state stream depth for jarvis's filter is zero.
